# 在真实成果工作区验证聚合流程

安装检查通过后，还要在工具 checkout 外验证实际宿主如何衔接各阶段。样本用于发现
缺陷类别；不要把目标名、某个 IPC 名称或某个保护器写成产品默认例外。

## 分阶段审查

1. 新工作区只接收哈希固定的原件副本和来源记录，不导入上次候选或把旧分析当新观察。
   记录实际对话、项目根、工具版本与范围。区分“明确点名 Reverse Fusion 的受控测试”
   和“自然任务描述触发入口”的测试；前者不证明后者每次都会遵守。
2. 检查实际调用和文件，确认全局入口、路由、领域正文、项目内 case、后续技术细化。
   比较工具发现、运行时、provider 操作、业务观察四层状态；每层独立记缺口。
3. 分析检查点由维护方审阅原材料。界面入口不代表功能可用，前端放行不代表后台
   放行；字符串、解压、反编译和一侧运行都不能替代行为模型。授权、设备、时钟、
   持久化、网络、并发及副作用作为相关行为的依赖调查，不要求每个无关功能都闭合。
4. 选取证据充分且副作用可控的有限切片检验交接。需要调整范围时，将决定追加到
   原 case，保留整目标未完成项。正式交接引用真实原材料；不借合成 bundle 通过门。
   先审查 spec/plan/tasks、unknown、比较规则与来源，再运行 Builder prepare。
5. 原版 oracle 来自固定原件，候选由另一份独立实现提供。若只运行原文件中的纯函数
   片段，固定原文件、提取区间、依赖、调用器及环境摘要；不得把重写的“原版”作为
   两侧比较。受限 VM 是调用环境，不是操作系统隔离证明。
6. 先冻结输入、比较规则和留出材料，再写候选。实现后分别验证规格符合、原版对照、
   独立运行；故意错误变体必须失败。执行缺失/超时/解析错误属于 unknown 或 fail，
   不能因为“两侧都没输出”得到等价通过。业务 proof 与文件边界 receipt 分开。
7. 出现偏离时停在当前检查点。若是产品缺陷，在共享工具仓库修复、补能复现该类
   问题的检查、更新 checkpoint、部署并同步；若是任务辅助脚本错误，在成果项目
   修复并记录，不能冒称所有同类目标已经通过。继续前重核发生变化的冻结输入。

## 需要跨目标保留的缺陷类别

| 类别 | 观察或反例 | 适用范围 |
|---|---|---|
| 工作区与传输 | cwd/显式根、空格/中文/非代码页字符、路径逃逸、不同进程编码 | EXE、APK、网站及普通开发 |
| 工具准备 | 缺少 provider、旧运行时、临时路径丢失、空参数、子进程失败及无关工具下载 | 所有 provider 启动 |
| 领域演进 | 安装器到载荷、JS 到 native/WASM、DEX 到 JNI/动态类加载 | 混合技术与困难目标 |
| 关键依赖 | UI 与后端不同门、授权/设备/时间/网络/缓存、功能停用与错误路径 | 与所选行为有实际依赖的任务 |
| 交接完整性 | 真实证据来源、旧/错摘要、跨 case、关键 unknown、先写代码后补规格 | 独立实现与追版 |
| 比较真实性 | 同源两侧、转调原件、缺失输出、错误变体不失败、环境/输入漂移 | 每项有限等价声明 |
| 运行与清理 | 新目录冒充隔离、无设备冒充设备运行、只看主 PID 冒充完整后代清理 | 动态分析及真实验收 |

JavaScript URL 转本机路径使用 `fileURLToPath`，不要手工裁剪 `URL.pathname`；
外部过程使用参数数组、明确字符编码和有限输出，将完整大输出保存为可检索文件。
辅助脚本也应在带空格/中文的路径下检查，而不是只验证产品主 CLI。

本清单指导补证和回归，不是一份“所有语言、保护器和远程服务均已通过”的证书。
当前实际结果始终以最新 checkpoint 和各成果 case 为准。
