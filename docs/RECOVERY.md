# 中断、失败和缺资料时如何继续

这份说明由智能体使用。用户只需说“继续”“这里不一样”或说明遇到的情况。
案例、Evidence、官方 Spec 和原生 Craft 记录继续各自负责真实状态，不另建状态账本。

## 先恢复原来的工作

在成果项目调用共享工具的 venv：

```text
[python] -m reverse_fusion workflow --project-root "[当前项目]" --case-root work/current-case
```

不知道案例名时省略 case-root：唯一开放案例直接恢复；多个案例先根据当前对话和
目标身份判断，仍有歧义才向用户确认。输出包含原话、最终意图、当前阶段、已保存
引用、REA/Spec/原生 Craft 的实际入口参数和工作目录；这是只读交接，不是业务完成。
共享工具路径由本次安装计算，不从旧聊天复制桌面缓存路径或其他电脑盘符。

活动 scope、workitems、结论等重要材料用 bridge 的 `--ref [项目相对文件] --record`
加入同一案例的引用。记录保存引用，内容仍在原文件，Evidence 身份和摘要不随意刷新。
不要把“继续”的短句写成一个新目标。正常开发无需建立逆向案例。

## 某个功能缺资料

先判断缺失会影响哪些任务，继续不依赖它的静态分析、资源/格式调查、调用关系、
独立比较准备或已满足依赖的实现。切片是完整目标中的步骤，不能取消其余要求。
智能体自行检查现有文件、可用工具和可行替代观察方法，不能把技术选择交给零基础用户。

只有确实需要人的操作、用户持有资料或产品决定时，才说明：缺什么、影响哪个功能、
为什么已有方法暂时不能回答、最小需要用户做什么。不要问完后把其他可继续工作也停掉。
可以先提出必要问题再继续独立工作；所有合法下一步都需要外部条件时保存进度等待。
不得编造未知服务响应、默认授权成功或降低最终效果来“完成”。

## 工具失败或部分成功

- 缺工具：区分必装核心缺失和目标专用工具缺失。核心缺失修复安装；目标工具按当前
  授权和本机环境准备或选替代方法。安装未完成不能靠模型直接写候选来冒充聚合。
- provider 超时、内存不足、解析失败、部分输出：先读实际状态、错误、coverage 和
  limitations。保存完整原始结果；退出码为零不能覆盖内部失败。针对问题调整输入
  范围、方法或预算。原始函数片段必须有原件身份、位置和依赖来源。
- 加壳/反调试/工具触发退出：加载相应领域及困难目标资料，检查观察者影响后选择
  下一证据动作。这里只规定判断责任，不固定工具顺序。
- 规格不支持实际行为：回到同一案例补调查或修规格；候选行为不符但规格正确则修候选。
  比较环境不同先修环境，缺失输出不能算一致，不改测试预期凑通过。

## 原生 Craft 批次中断

```text
[python] -m reverse_fusion workflow --project-root "[当前项目]" --case-root work/current-case --receipt "[原session记录]"
```

只读输出会检查项目/案例归属和冻结文件是否改变。它不会启动工具、更新摘要、删除
文件或替你确认进程已经退出。读取同一 lease 对应的 `.events.jsonl`、原生 craft.json、
session 的 phase 和已执行检查。先确认原生调用与其拥有的命令已退出、单写者无冲突。
状态未知先查清，不启动第二写入者；不能用“进程列表没看到名字”替代严格清理证据。

- 冻结输入没变、写入者已退出：按原租约继续尚未完成的写入/修正和全部冻结检查。
- 检查失败：保存失败，修候选，再运行本批全部必要检查；失败不允许作为完成。
- 需要改研究、范围、规格、任务或命令：保留旧批次和输出，结束/隔离旧写入者，重新
  审查后创建新的 lease、receipt 和工作区。不能改旧摘要绕过冻结检查。
- prepare 失败：保留失败输出，检查是否留下部分工作区、lease 或 session。未确认
  无活跃写入者前不删除；使用明确的新批次路径重试，不能把旧候选误当本次产物。
- 批次需要放弃或冻结研究已改变：创建项目内请求文件 `{"reason":"本批中止的实际原因"}`，
  调用 `native-craft abort --project-root [当前项目] --lease [原租约] --params-file [请求文件]`。
  原生操作获取同一工作区写锁；活跃操作占锁时拒绝。它保留候选、旧摘要、失败记录和
  改变的输入列表，将原session置为aborted；这不是成功候选，也不重新冻结研究。
  此后旧批次不能继续写或finish，需要新审查/租约/工作区。租约本身被改动则仍拒绝，
  先从不可变记录恢复租约身份；不能借中止修改原工作区归属。
- 原生检查完成：执行 return_summary、cleanup，再对同一 receipt 做附加 session
  check/refine/finish；之后才更新官方 Spec tasks/converge，并独立比较实际结果。
  finish会核对原生cleanup及其对应的精确候选摘要；绕过cleanup或随后修改候选均拒绝。
- 批次 finished：后续候选修改创建新批次。finished 只结束该批工具交接，完整用户
  目标还要根据真实比较、尚未完成的需求和用户交付决定判断。

源代码、补丁或混合交付采用同样的目标保留、来源、构建/修改、比较、回滚和恢复要求。
需要改变用户收到什么产品时先解释影响并取得决定；不同技术形态不能消除验收要求。
