# Decisions

## RF-025 Shared core with thin host adapters

User clarified2026-11-16: host adaptation completion does not require logged-in
full-model runs for every host. Qualify the common Reverse/REA/Spec/Craft and
comparison/recovery core through representative Codex/Pi full use; check actual
entry names, skill discovery, tool invocation/permissions, project cwd, official
Spec layout and connection lifecycle for each adapter. Three-host connection/
removal and actual generated Spec discovery regressions passed again. Claude
project adapter is complete; full model-use observation remains unperformed.
Do not turn that observation into a mandatory login request or release blocker.
New hosts need concrete contract mapping and focused tests for changed protocol,
permission or process semantics, not blanket automatic support or repeated full
reconstruction. New operating-system distributions still need native/runtime
qualification. Preserve past failures and do not fabricate host runtime results.
Canonical criteria: docs/HOST-PROJECT-CONNECTION.md.

## RF-024 Completion requires executable failure exits

RF-31 reopens the RF-30 engineering label for reproduced implementation gaps:
formal failed-batch abort, native-to-observer completion binding, candidate
fixity after checks, and installer I/O rollback. Native adapter0.1.1 still uses
the same pinned upstream engine and host reasoning; its new distribution carries
the updated source identity. Deployed release readiness additionally requires
source-bound regression logs, not just nonempty files or parseable CLI handlers.
The durable completion order and original22requirements are in COMPLETION-PLAN.md.
No additional user target, sample chat or universal equivalence claim is required.

## RF-023 Finite current-host engineering release

The user's RF-30 instruction explicitly requests a full version without more
samples/real-target testing as release prerequisites. Deliver1.1.0 for the
already prioritized Windows x64/Codex host. Preserve real component ownership,
semantic readiness, full user objective and actual target acceptance. Separate
engineering completion from unexecuted target/host qualification; do not turn
unknown future software into an infinite release gate or relabel it as passed.

The read-only workflow view derives original goal, project refs, component argv
and frozen session drift from existing records, without another Evidence ledger.
Missing dependencies block only affected work. The finite manifest checks
source/doc contracts and actual CLI handlers; --deployed also checks platform,
core identities, current receipt and exact installed managed entry. It does not
execute targets or pretend to verify model judgment. Existing real native tests
and earlier finite composition remain separately scoped evidence.

## RF-001 Single repository

This project is published as one GitHub repository. Official components are described by manifests and fetched through their official distribution; owned enhancements live in this repository.

## RF-002 Official by default

REA and Spec Kit remain official until a documented capability gap justifies a
local fork. RF-28 superseded the earlier interface-only Craft design: the current
owned seam drives the real pinned engine and distributes a replayable Windows
Process patch. The four older patch names remain historical provenance only.

## RF-003 Old projects are read-only

The old reverse-skill, old installer, existing REA/Craft/Spec Kit installations and current host configuration are outside this repository's write scope.

## RF-004 One CLI

The repository exposes one `reverse-fusion` CLI with plan/install/doctor/accept/update/uninstall/handoff/contracts subcommands. Small checks are modules, not separate command scripts.

## RF-005 Persistent handoff

The repository stores project context, current state, source manifest, decisions, upstream policy and checkpoints so a new agent can resume after context compression.

## RF-006 Portable local Reverse owner

RF-17 makes `components/reverse-core/router.py` and its versioned
`routing.json` the default route owner. The previous enhanced `reverse-skill`
remains a read-only, explicitly selected compatibility source. This closes the
fresh-clone receipt dependency without introducing a second runtime route owner.

## RF-007 Host-owned Builder and model boundary

The repository owns task scope, output paths, checks and cleanup. The current
Codex/Pi/Claude host owns its account, provider and model; no model is selected
or downloaded by Reverse Fusion. The default Builder is that agent in the
current conversation, not another CLI invocation. Frozen-input and allowed-write
observations are separate from independent business acceptance. Child CLI
transport is optional and has its own live login/quota/cleanup status.

## RF-008 Bounded target ledgers

Each representative target has its own Spec tasks, original/candidate Evidence,
comparison, proof and obligation ledger. A ledger may close a reviewed bounded
obligation while retaining REA-generated unknowns for package, parser, device or
dynamic behavior outside that case; those unknowns are recorded explicitly.

## RF-009 APK provider bootstrap

The official `jadx-headless-mcp@0.7.1` bridge is caller-supplied through a
repository-local checksum manifest and bootstrap script. The JAR is ignored
from Git history and is never installed into global JADX, REA, Java or host
configuration.

## RF-010 RF-22 completion label

`reconstruction-product-v1-final` is written only after the four representative
chains, host Builder, three-state acceptance, fresh-clone lifecycle, provider
boundaries and documentation consistency have direct Evidence. Future targets
start new cases or small capability updates; they do not reopen the completed
product architecture merely because every variant was not pre-executed.

## RF-011 Nested subcases

Normal development is a host-native baseline, not a separate universe. A main
project may create an isolated analysis or reconstruction subcase at any point:
the subcase owns its target path, route, Evidence, tasks and candidate; only
reviewed Evidence-backed conclusions flow back into the main project. This
allows a website, desktop application, APK or another project to be researched
mid-development without forcing every main project into reconstruction mode.

## RF-012 Local domain skill ownership

The new repository carries a pinned copy of the enhanced reverse-skill domain
skill bodies under `skills/`. Route metadata alone is insufficient for a fresh
clone; the local route reports `unavailable` when its descriptor or referenced
skill body is missing. The old reverse-skill checkout remains read-only and
optional compatibility input.

## RF-013 Evidence and host-boundary records

Representative records live under the stable `evidence/rf22/` path. RF-25 found
that path normalization had changed hash-covered fields without changing IDs;
it replaces those invalid records with raw authenticated runs. Historical
absolute paths are observations, not deployment configuration. Contracts check
file hashes; official REA additionally checks identity, bundle links and a real
tamper counterexample. Optional host calls compare known configuration hashes;
changed/unobservable snapshots and uncertain descendant cleanup are never
declared verified merely because the root invocation returned.

## RF-014 Preserve content and executable handoff separately

RF-24 audits enhanced reverse-skill at its recorded pin. Skill text equality is
not sufficient when a domain references resources outside skills or a route
does not carry downstream context. Restore those supporting resources, publish
current portable rules, expose required reads, and report missing resources.
Keep hard-target methods adaptive and provider neutral. The 603-file inventory
records exact current upstream/local digests and adaptation reasons; it is
content preservation, not target runtime acceptance. All local route entries use the product JSON; the
original skills JSON remains the original compatibility baseline.

## RF-015 Repository-stored deployment and honest scope

`docs/AGENT-BOOTSTRAP.md` is the only deployment action contract. The user gives
the repository link; the selected current host discovers paths and installs a
local venv/receipt. Analysis does not require reconstruction tasks. Uninstall scripts remove the
local venv/receipt, retain vendor/case assets and implement no transaction journal.

## RF-017 Codex cross-project adapter

When Codex is the selected host, install writes a user-level `reverse-fusion` skill
and a marked global `AGENTS.md` block that point to this checkout's router. The
adapter is deliberately thin: it preserves the current project as the work area,
does not copy domain skills, choose models, or start providers, and can be skipped
with `--no-global-adapter`. Uninstall removes only the managed block and skill.

## RF-016 Bounded integration proof authority

Repository-owned bounded verifiers may use the pinned official REA serializer
under the explicit integration exception in `skills/reconstruction/SKILL.md`.
They must recheck artifact hashes, perform the declared finite observations and
retain links. They do not impersonate REA native process verification. Web's
bounded answer ledger is separate from its complete graph's open obligations;
APK manifest/member equality does not prove method-body or device equivalence.

## RF-018 Explicit task project boundary

The shared checkout owns code, skills and provider installation; the caller's
project owns cases, tasks, candidates and task receipts. Task commands default to
cwd and accept `--project-root`. Lifecycle and fixture acceptance commands remain
tool-checkout operations. A successful route is not a completed component run.

## RF-019 Case-bound implementation handoff

Before implementation in a recorded reconstruction case, Builder prepare reuses
the inherited handoff checker and freezes its dependency files and a separate
semantic review record. Declared critical unknowns and stale references block it.
No new Evidence or obligation ledger is created. Mechanical PASS cannot discover
omitted dependencies or validate a caller's scope decision; a generic unbound
session only observes file boundaries and cannot certify reconstruction readiness.

## RF-020 Repository runtime selection survives project changes

An explicit compatible Node selected for REA bootstrap is recorded in the tool
checkout's ignored runtime receipt, after engine and package integrity checks.
Python diagnosis/acceptance and Windows provider runners restore that selection
without changing global PATH or host configuration. Environment/explicit options
take precedence; copied, missing or malformed receipts fall back to discovery.
The runtime receipt is an executable-path choice, not health, Evidence or proof.

## RF-021 Required real components supersede interface-only completion

The user requires installed REA, official Spec Kit and actual Craft participation
in reconstruction. Missing components cannot be accepted by substituting host
Markdown or a session observer. Windows default install bootstraps all core
components and a local compatible Node when needed, then selected-host install
rejects missing runtimes. Normal development and analysis retain their stages.

The owned Craft external-writer seam links the fixed upstream Rust engine;
the current host supplies reasoning/content to real Workspace and build tools.
A reproduced Windows quoted-command gap is fixed by a replayable source patch,
with source/patch/binary/archive identity and real timeout/descendant/lock tests.
This authorized adaptation avoids an unrelated second Study/model/account.
Official generated Spec workflow and its prerequisites are executed in the
outcome project. Tool/runtime qualification stays separate from original/candidate
comparison, native REA evidence and finite target obligations. Historical RF-25
interface checks remain historical, not the current product completion gate.

## RF-022 Plain-language objective survives technical routing

The user supplies the goal, not specialist commands. The first case record
retains the original request and delivery objective independently from the
current stage. A reconstruction request starts domain analysis; actual evidence
refines that same case. Technical hints and a short continuation cannot replace
the full objective or silently approve a subset. When the first route was only
read-only, --user-request preserves the original goal at first record. Implicit
continuation resumes a unique open local case and reports ambiguity otherwise.

The real novice chat found the first-record gap after controlled component tests
had passed. It is retained as a failed run; fixes are tested in another new chat
without previous analysis or a specialist prompt. The agent workflow and beginner
guide define useful user communication, evidence-based readiness and whole-goal
preservation; they do not prescribe a fixed reverse tool sequence. Real component
qualification and independent novice entry observations are reported separately.
