# Reverse Fusion 1.1.0 完整工程版

本次交付范围为 **Windows x64 + Codex 桌面端**：安装实际 Reverse/REA/官方 Spec Kit/
真实 Craft，提供跨项目入口、适用领域、分析到实现交接、比较修正、错误恢复、更新
与卸载。继续使用当前 Codex 的模型。Pi/Claude 的完整接入和其他平台分发是后续版本。

## 有限的交付标准

用户不需要再提供软件样本，项目也不因某个测试软件尚未复刻完成而无限延后发布。
这次不新开真实目标测试，不恢复之前的换肤软件对话。工程交付依据是实际实现审查、
本仓库回归检查、安装组件身份及已经存在的组件运行记录。历史记录保留日期与范围，
不能冒充1.1.0对新目标的运行证明。

机读清单在 `release/manifest.json`。检查入口：

```text
[python] -m reverse_fusion release-check
[python] -m reverse_fusion release-check --deployed
```

第一项检查仓库合同、版本、交付文件、可解析的实际 CLI 交接入口。第二项还检查当前
支持的平台、真实组件安装身份、当前版本安装记录和最新全局入口。检查不启动目标，
不分析样本，不替智能体判断“行为已经理解”，也不输出任何目标等价通过。

## 这次补齐的使用链

用户在任意成果项目说需求 → 全局入口 → 保存原话和完整目标 → 领域分析 →
根据证据选工具和下一动作 → 就绪审查 → 官方 Spec 生成工作流 → 真实 Craft 工具
实现与检查 → 独立比较 → 修候选或回分析/规格 → 交付并保存下一次恢复所需记录。

这个顺序描述职责交接，领域内部的方法和反复次数由模型据实判断。分析任务不强制
进入编码，普通开发保留宿主原有方式。各组件入口现在随 bridge 返回，workflow 可以
只读恢复现有案例及冻结记录。模型不必从旧聊天里猜安装位置或自行拼接不同版本流程。

遇到未知或需要用户协助时，先推进独立工作，只把真正依赖人的部分交给用户，规则见
[RECOVERY.md](RECOVERY.md)。缺事实不能靠猜测实现，程序复刻结果仍需对应任务的
实际运行与比较，不能把工程发布状态套到软件成果上。

## 什么算本版本交付完成

- 交付清单中的实现、组件和必要文档齐全，相关代码回归检查通过。
- 本机Codex实际部署指向当前checkout和本版本，缺任何核心组件都不能过部署门。
- 新功能可在现有项目中恢复并找到实际组件入口，缺引用、跨案例或冻结变更能明确返回。
- GitHub同步代码、补丁、清单和说明；用户不用保存本聊天的专业提示。

这些是有限、能执行的工程完成条件。任何新软件都另有其输入、运行环境和业务验收，
不被当成本版本缺少实现的替身，也不预先获得成功结论。
