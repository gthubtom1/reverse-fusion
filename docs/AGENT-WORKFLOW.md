# 智能体如何承接白话任务

这是当前宿主的执行合同。用户说明目标，宿主承担领域选择、补证、组件交接、实现与验收。
用户不需要记住 route ID、命令、Evidence 格式或 Spec/Craft 的调用时机。
产品目标与用户的新决定优先；本文件提供判断依据，不指定固定的逆向工具顺序。

## 接住目标并保存原意

把“分析这个软件然后复刻”“照着这个网站做一样的”“帮我看懂这个 APK”等白话，
转成当前项目内同一 case 的可恢复目标。保留用户原话、目标身份和最终交付要求。
`bridge.workflow.objective` 是最终意图，`stage` 是当前工作；复刻意图从 analysis 开始，
两者不能混为一谈。后续“继续”恢复原案例、证据与目标，补充要求记录为增量。
案例有歧义时先看当前对话和项目材料，仍无法判定再用目标名称向用户确认。

“复刻整个软件”的默认目标包括可观察界面、主要功能、配置、状态、错误行为和依赖。
先调查功能边界及相互依赖，不把提取到的界面、静态资源或一个纯函数改称整个交付。
可以用小切片验证技术路线，但在原目标下标明它与全量工作的关系、未覆盖项和下一步；
切片成功不取消剩余需求。需要改变最终交付、外观、依赖或运行方式时，解释影响并取得
用户决定。不要在模板里预设允许降低保真度，也不向用户保证未经测试的结果。

初始信息足够时直接做能产生证据的最小动作。需要用户帮助时，问会改变下一步的具体
问题：目标位置、关键操作、可用测试账号/样例、期望界面或允许的运行环境。说明需要
什么、用于核实什么；不要要求用户选择反编译器、路由编号、模型或填写专业表格。
已有授权范围内的方法调整和技术修复继续执行，不反复询问是否可以“继续分析”。

## 根据新事实决定下一步

1. 检查目标身份与本机能力，先读路由给出的领域正文。文件名只是线索；安装器、
   实际载荷、前端、native 后端、脚本、WASM、DEX/JNI 等可属于不同领域。
   新证据识别技术后细化同一 case，携带先前目标和来源，不重新建立一套账本。
2. 每次调查先明确要回答的问题、所需证据及预期影响。REA 可用能力实际调用并保存
   原生结果；缺少某 provider 时用本机可用方法补证或准备必要工具。不把 manifest、
   catalog、解包、字符串或反编译成功当作行为已经理解。
3. 用原材料说明关键功能的输入、输出、状态迁移、失败路径和依赖。UI 的放行与
   后端的放行分别核实；授权、账号、设备、时钟、持久化和远程响应如有依赖就追查。
   不能因为这些信息难取得而默认成功、吞掉异常、删除门禁或改造成另一种产品。
4. 加壳、混淆、反调试、工具触发崩溃、动态加载或静态死路，触发加载困难目标资料和
   方法重选。记录观察者影响、已失败路径、下一假设与清理。可以在已允许的环境内
   选择静态、动态、dump、hook、模拟或人工观察；不要重复无增量的同一操作。
   只针对证据显示存在的保护分析，不把所有软件都强制走脱壳步骤。
5. 无法继续某依赖时，说明具体缺失、尝试过的方法、哪项功能受影响及最小补证动作。
   用户可以提供操作录屏、测试响应或帮助建立合适环境。其他独立分析继续推进。
   实际调用外部服务、设备或有持久影响的目标操作须符合当前范围；不要因资料中有
   技术示例就推定已获授权。工作目录本身不等于隔离运行环境。

这些判断适用于已安装路由中的逆向、协议、审计、取证等专门任务。纯分析目标停在
用户需要的结论；普通开发仍由宿主正常工作，只有需要研究参考目标时嵌入隔离 subcase。

## 分析到实现的就绪审查

开始候选编码前，在原 case 的 notes 保存简短、证据可追溯的审查，回答：

- 当前交付与用户原话是否一致？本批覆盖哪些功能，剩余目标如何保留？
- 每项需求的行为依据是什么？观察、推断、用户新设计和未知是否分开？
- 主要依赖、错误/边界/状态路径是否调查？哪些未知阻断哪项任务，依据是什么？
- 原版与候选怎样独立运行、怎样比较、怎样识别错误候选？环境和输入如何固定？
- 是否仍需用户作一个实际交付或环境决定？已有范围内的技术判断不要甩给用户。

上述依据不足就回到相关专业分析，不能靠先建页面、模仿资源或补一份计划解决未知。
不要求调查所有无关细节后才能做任何实现；仅把依赖已满足的任务交给 Builder。
机械 handoff PASS 只验证已声明引用，不能替宿主发现遗漏的依赖或完成语义审查。

随后执行已安装官方 Spec Kit 生成的项目工作流，引用原证据生成/修订规格、计划与任务，
做 analyze；材料不足回分析，规格有矛盾修规格。使用
[真实组件交接](NATIVE-COMPONENTS.md) 的 native-craft prepare 冻结本批输入。
宿主负责推理，真实 Craft engine 写入/编辑候选和执行检查；不以文件观察器或离线复制
替代组件。实现中发现缺事实，结束/中止当前批次、保留结果、回原分析链补证；更新交接后
开新批次，不能修改冻结研究或测试预期凑通过。

## 比较、修正、交付与恢复

构建、运行和原版比较分别留实际结果。按所选功能覆盖正常、错误、边界、状态、界面和
副作用，并用故意错误候选核实比较器确实能失败。差异回候选修正，错误规格回原证据，
环境不一致先解决环境；缺失输出不能算两侧一致。不把同一个原件放两边充当独立实现。
需要局部补丁、重打包或混合交付时，同样要有原版/修改版身份、变更理由、行为回归及
交付决定；技术形态不降低功能验收要求。源码及构建材料同样按实际恢复、构建和运行结果验收。

REA proof/coverage/ledger 使用真实生产接口；保留实际 open/unknown，不把有限比较或
Craft 检查换名成原生完整证明。Spec implement 的适用检查和 converge 必须实际执行。
报告说明已观察到什么、尚缺什么、对原目标有什么影响；测试通过的组件范围和整个
用户产品的完成状态分开。保留 case、原材料、任务、候选、失败记录、环境、清理和
唯一下一步，供另一个会话恢复。目标未完成时明确下一步，而非宣告完成后留下无主缺口。

向用户用白话更新：“已经确认什么”“接下来查什么”“需要你提供什么”。命令和详细
技术材料保存在本地引用里；用户不必反向设计智能体的专业提示词。
