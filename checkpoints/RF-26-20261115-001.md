## Purpose

This checkpoint answers whether Reverse Fusion is a real multi-component product
or only a collection of files. It rechecked the local router, all 45 route
descriptors and skills, mixed-domain requests, reconstruction handoff, selected
host boundaries, and fresh-clone documentation. The old reverse-skill checkout,
old installer, host credentials and global configuration were read-only.

## Architecture result

The product is a repository-level orchestrator with one default local Reverse
route owner. It keeps the enhanced Reverse domain content locally and exposes
REA, Spec and Builder through explicit stage contracts; it does not merge all
upstream programs into one monolith or load every skill into every conversation.

`bridge` now returns:

- a primary route and its concrete required reads;
- `related_routes` with secondary descriptors, skills and required reads for
  mixed tasks;
- `next_stage` pointing to R46 when the request contains reconstruction intent;
- a `workflow` object describing stage, required artifacts, activation boundary
  and business-acceptance boundary.

`normal-dev` is host-native by default. Reverse is activated by an explicit
analysis/reconstruction mode or a clear reverse intent. `follow-up` requires an
existing open case and reuses its refs; a missing case is typed `blocked`.
Downstream providers remain on demand, so the workflow guides the host without
forcing a fixed tool order or limiting model reasoning.

## Known boundaries

The route benchmark does not prove every future target or provider. Tool index
is generated per machine and ignored by Git; missing tools remain unknown. Only
12 of 45 routes currently have route-specific hard-target overlay playbooks;
the shared hard-target decision framework remains available to all routes.
`skills/config/routing.json` remains the fixed upstream baseline and intentionally
differs from the product's local routing additions; default execution uses the
local file. Craft native R46, Android device execution, full Web graph closure,
Windows PTY descendant cleanup and uninstalled provider capabilities keep their
RF-25 typed boundaries.

The checkpoint is a product architecture closure, not a claim that every
future protected binary, APK, web app or provider has already passed.
